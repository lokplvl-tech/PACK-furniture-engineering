# Ключевые различения: Мебельный инжиниринг

> Источник: FPF A.7 (Strict Distinction)
> Критерий: если два термина часто путают - это различение.
> Источник материала: `06-sota/datum-mebel-epistemic-standard.md` (внутренний стандарт компании «Датум Мебель»)

---

### FE.D.001: Объект vs Описание

**Maturity:** seed

**Definition**: Объект - реальная физическая мебель у клиента; Описание - её виртуальная модель в CAD-системах семейства «Базис».

**Contrast with**: Описание не есть сама мебель - это информационная абстракция, которая может расходиться с физической реальностью.

| Объект | vs | Описание |
|--------|-----|----------|
| Физическая материя в помещении клиента | | Цифровая модель в семействе «Базис» |
| Существует независимо от CAD | | Существует только в системе проектирования |
| Проверяется измерением | | Проверяется визуально/логически |

**Why it matters**: путаница Объекта и Описания - корень эпистемологического разрыва: дизайнер может считать проект готовым, потому что модель выглядит правильно, хотя физический объект (помещение) уже не соответствует модели (например, ремонт после замера).

**Related items**:
- Failure Modes: коллизия при монтаже (см. §5 Guards источника)

**SoTA**: `current`
- Revision criterion: смена CAD-платформы или методологии замера.

### FE.D.002: Описание vs Спецификация

**Maturity:** seed

**Definition**: Описание - рабочая CAD-модель; Спецификация - нормативный документ (законченный список свойств), обязательный для производства.

**Contrast with**: Спецификация не есть сам процесс проектирования - это его юридически и технологически обязывающий результат.

| Описание | vs | Спецификация |
|----------|-----|--------------|
| Может меняться в процессе работы | | Фиксирована после подписания |
| Инструмент дизайнера | | Закон для Фабрики |
| Черновой статус | | Финальный, обязывающий статус |

**Why it matters**: Фабрика не имеет права трактовать Описание - только Спецификацию. Смешение уровней ведёт к тому, что производственные решения принимаются на основе незавершённой модели.

**Related items**:
- Roles: Дизайнер-конструктор (создаёт Описание), Технолог (конвертирует в Спецификацию)

**SoTA**: `current`
- Revision criterion: изменение регламента подписания заказа в инструментах семейства «Базис».

### FE.D.003: Work Scope vs Claim Scope

**Maturity:** seed

**Definition**: Work Scope - объекты, на изменение которых у роли есть права и бюджет; Claim Scope - строгие границы истинности данных этой роли.

**Contrast with**: Work Scope отвечает на вопрос «что я могу менять», Claim Scope - «на какие данные я имею право ссылаться как на истинные».

| Work Scope | vs | Claim Scope |
|------------|-----|--------------|
| Право действия | | Право утверждения |
| Например: Дизайнер меняет модель | | Например: геометрия L4 истинна на момент замера |
| Нарушение - самоуправство | | Нарушение - фальсификация данных |

**Why it matters**: конфликт «Принципал-Агент» (дизайнер оптимизирует локально) возникает именно на стыке этих двух scope - агент выходит за границы истинности данных, которые ему не принадлежат.

**Related items**:
- Roles: Клиент (Claim Scope на L4 до ремонта), Дизайнер-конструктор

**SoTA**: `current`
- Revision criterion: изменение договорной модели (кто и когда фиксирует акт замера).

### FE.D.004: Изоморфизм vs Сходство

**Maturity:** seed

**Definition**: Изоморфизм - строгое, однозначное структурное подобие между узлом CAD-модели и физической деталью; сходство - произвольное, не гарантирующее взаимной однозначности подобие.

**Contrast with**: Сходство допускает исключения и приближения; изоморфизм - нет.

| Изоморфизм | vs | Сходство |
|------------|-----|----------|
| Однозначное соответствие 1:1 | | Приближённое, «похоже на» |
| Проверяемо на станке ЧПУ | | Не проверяемо формально |
| Нарушение = коллизия | | Нарушение = просто неточность |

**Why it matters**: станки ЧПУ требуют изоморфизма, не сходства - погрешность даже в 1 мм (не «примерно похоже») уже физическая коллизия при сборке.

**Related items**:
- Failure Modes: погрешность присадки >1 мм (§7.1 источника)

**SoTA**: `current`
- Revision criterion: смена станочного парка на менее точный/более точный.

### FE.D.005: Гвард (Guard) vs Рекомендация

**Maturity:** seed

**Definition**: Гвард - жёсткий барьер, физически блокирующий переход проекта на следующую стадию при нарушении инварианта; рекомендация - совет, который можно проигнорировать без остановки процесса.

**Contrast with**: Рекомендацию можно нарушить и продолжить работу; гвард - нельзя, стадия не пройдена.

| Guard | vs | Рекомендация |
|-------|-----|--------------|
| Блокирует переход на след. стадию | | Не блокирует ничего |
| Контролируется ролью (Технолог) | | Не требует контролёра |
| Нарушение = брак | | Нарушение = субъективный минус |

**Why it matters**: вся система эпистемологического контроля (§5 источника) построена на гвардах, не на рекомендациях - иначе коммерческая мотивация Дизайнера всегда победит «мягкий совет».

**Related items**:
- Failure Modes: все 9 записей §5 Guards источника

**SoTA**: `current`
- Revision criterion: появление нового класса нарушений, не покрытого текущими 9 гвардами.

### FE.D.006: Инвариант vs Настраиваемый параметр

**Maturity:** seed

**Definition**: Инвариант - физическая величина, неизменная при любых проектных трансформациях (например, зазор 41/51 мм); настраиваемый параметр - величина, которую дизайнер вправе менять под конкретный проект (например, цвет фасада).

**Contrast with**: Инвариант нарушать нельзя ни при каких обстоятельствах; параметр - можно и нужно адаптировать под клиента.

| Инвариант | vs | Настраиваемый параметр |
|-----------|-----|--------------------------|
| Одинаков для всех проектов | | Уникален для каждого проекта |
| Источник - физика/регламент | | Источник - вкус клиента |
| Пример: зазор от трубы отопления 35 мм | | Пример: цвет цоколя |

**Why it matters**: смешение этих двух категорий - типичная ошибка новичка: попытка «оптимизировать» зазор как если бы это был эстетический параметр.

**Related items**:
- Directories: Таблица 7.1 источника (все технологические зазоры)

**SoTA**: `current`
- Revision criterion: изменение строительных норм или регламента поставщика фурнитуры.

### FE.D.007: Тандембокс vs ПВШ

**Maturity:** seed

**Definition**: Тандембокс - система выдвижного ящика с несущей способностью 30-50 кг; ПВШ (полно-выкатные шариковые направляющие) - телескопическая конструкция с нагрузкой до 20 кг.

**Contrast with**: Внешне оба - выдвижные механизмы, но несущая способность отличается более чем в два раза - это не взаимозаменяемые решения.

| Тандембокс | vs | ПВШ |
|------------|-----|-----|
| 30-50 кг | | до 20 кг |
| Стандартный выбор для кухонь | | ТОЛЬКО ящик 120 мм под духовым шкафом |
| Металлические боковины + рейлинг | | Полозья с шариковым ходом |

**Why it matters**: MUST NOT-правило (§6 источника) прямо запрещает ПВШ в стандартных выкатных модулях именно из-за этого различения по нагрузке - визуальное сходство механизмов маскирует разницу в несущей способности.

**Related items**:
- Directories: Таблица 7.7 источника (характеристики фурнитуры выдвижения)

**SoTA**: `current`
- Revision criterion: появление новых моделей направляющих с изменённой грузоподъёмностью.

### FE.D.008: Холон vs Модуль

**Maturity:** seed

**Definition**: Холон - узел холархии, одновременно автономное целое на своём уровне и зависимая часть системы выше; модуль - конкретный физический холон уровня L2 (нижний, верхний, пенал, метровик).

**Contrast with**: «Модуль» - частный случай холона (конкретный уровень L2); не всякий холон - модуль (например, L3-гарнитур или L0-субстрат - тоже холоны, но не модули).

| Холон | vs | Модуль |
|-------|-----|--------|
| Общее понятие холархии L0-L6 | | Частный случай, уровень L2 |
| Целое-и-часть одновременно | | Конкретная сборочная единица |
| Пример: L3-гарнитур, L1-деталь | | Пример: нижний модуль, метровик |

**Why it matters**: без этого различения легко спутать уровень абстракции при обсуждении проекта - «модуль» не описывает весь гарнитур (L3) или отдельную деталь (L1), только промежуточный узел L2.

**Related items**:
- Extended Kinds: HOL (Holon) в 00-pack-manifest.md

**SoTA**: `current`
- Revision criterion: пересмотр холархии (добавление/удаление макроуровня).
