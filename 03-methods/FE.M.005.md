## [FE.M.005] Разрешение проектных коллизий (цикл АДИ)

### Definition

Метод систематического поиска решения, когда в проекте обнаружен физический конфликт ограничений (например, газовая труба оказывается в зоне, где по стандартной схеме должен стоять тандембокс) — вместо интуитивного «на глаз» подбора первого приемлемого варианта. Название АДИ — по трём последовательным шагам рассуждения: Абдукция (генерация гипотез) → Дедукция (логическая проверка) → Индукция (эмпирическая проверка моделированием). Источник: `06-sota/functional-space-systems-engineering.md`.

### Purpose

Даёт репликируемую процедуру для ситуации, которая по определению не покрыта готовым гвардом (гварды перечисляют уже известные типовые ошибки — этот метод нужен именно тогда, когда конфликт новый или редкий, и типового решения ещё нет). Заканчивается либо чистым решением, либо явной меткой согласованного отклонения ([FE.WP.002](../04-work-products/FE.WP.002.md)), если ни одна гипотеза не даёт решения без остатка.

### Inputs

| Input | Description | Required? |
|-------|-------------|-----------|
| Обнаруженная коллизия | Конкретный конфликт физических ограничений на конкретном объекте (не абстрактный риск) | Yes |
| Действующие инварианты | Гварды, характеристики, ограничения фабрики (сроки, стоимость) — то, против чего проверяются гипотезы | Yes |

### Алгоритм разрешения

1. **Абдукция (генерация гипотез).** Сформулировать минимум 2-3 конкурирующих варианта решения. Пример из источника (труба в зоне тандембокса): (А) вырез в ящиках — занижает полезную площадь; (Б) отодвинуть ярус от стены на 100 мм; (В) заменить ящики на распашной фасад с полками.
2. **Дедукция (логическая проверка).** Каждую гипотезу проверить против уже известных инвариантов фабрики и Pack'а без построения модели — на бумаге/в голове. Пример: вариант Б при проверке требует столешницу шириной 700 мм вместо стандартной → тянет за собой увеличение срока на 30 дней и удорожание → отклонён на этом шаге, до траты времени на моделирование.
3. **Индукция (эмпирическая проверка).** Оставшуюся жизнеспособную гипотезу смоделировать в САПР «Базис-Салон» и проверить на отсутствие НОВЫХ коллизий (например, столкновение со стеной), которые не были очевидны на шаге дедукции.
4. **Итог: идентификация WLNK (Weakest Link, слабейшее звено).** Выбирается не «идеальное», а решение с наименьшей системной уязвимостью. Если по итогу всех трёх шагов остаётся неустранимый компромисс, а клиент готов его принять — оформляется [FE.WP.002](../04-work-products/FE.WP.002.md) (метка согласованного отклонения), и только после этого проект допускается к дальнейшему шагу.

### Key Distinctions

- Коллизия, разрешаемая циклом АДИ, отличается от нарушения, покрытого готовым гвардом (`05-failure-modes/`): гвард — это уже известный типовой сбой с готовым запретом; цикл АДИ — процедура для нового или редкого конфликта, для которого готового правила ещё нет.

### Failure Modes

_Формальной карточки FE.GRD пока нет. Наблюдаемый риск: пропуск шагов Дедукция/Индукция и переход сразу к «первому подходящему варианту» — теряется главная ценность метода (систематическая проверка вместо интуиции), риск скрытой новой коллизии. Кандидат на будущую карточку гварда._

### SoTA Status

**Status**: `hypothesis`

**Basis**: Источник единственный, синтезированный (не первичный документ компании, не кросс-валидирован независимым вторым источником, в отличие от большинства методов Pack'а — см. `06-sota/functional-space-systems-engineering.md`). Метод логически состоятелен и согласуется с уже известной практикой (пример из источника про газовую трубу и тандембокс использует реальные числа, совпадающие с независимо подтверждённой геометрией), но сам трёхшаговый процесс как формализованная процедура пока не подтверждён вторым независимым источником отрасли.

**Revision criterion**: Пересмотреть статус на `current` при появлении второго независимого источника, описывающего аналогичную процедуру разрешения коллизий (не обязательно теми же словами «Абдукция/Дедукция/Индукция» — важно совпадение по сути шагов).
