## Позиция 1 — Три царских вопроса

1. **Как называется метод?** P2W — «Принципы в работу» (Datum Mebel), код `FE.M.001`.
2. **Из скольких позиций состоит?** 8 позиций верхнего уровня (1, 2, 3, 4, 5, 6, 7, 8) — совпадает с формулировкой во frontmatter источника: «Строгий 8-шаговый алгоритм». Позиции 2 и 3 внутри себя дробятся на два действия каждая (2a/2b, 3a/3b) — это учтено на позиции 3 ниже, не как отдельные ветки силуэта.
3. **Как называется каждая позиция?** Claim Scope → Нижний ярус → Столешница и мойка → Техника → Верхний ярус → Панели → Фасады → Гейт Технолога.

## Позиция 5 — Проверка шампура

Каждая ветка выше — один вход сверху (`[Начало ветки]`), один выход снизу (`[Конец ветки]`), одна вертикаль; локальные циклы исправления («нет → назад к Вопросу») возвращаются на ту же вертикаль, не создают второй вход в блок. Проверено по всем 8 веткам — нарушений не найдено.

## Позиция 6 — Проверка запретов

- Нет пересечений линий между ветками (все межветочные переходы — именованные Адреса, не пересекающиеся линии).
- Нет обрывов: каждая ветка либо ведёт Адресом к следующей, либо (ветка 8) завершает силуэт.
- Нет «сиамских близнецов» (двух одинаковых развилок подряд без действия между ними).
- Единственный вход в ветку — через её начало: соблюдено даже для входа в ветку 8 из цикла исправления гварда (адрес ведёт на начало ветки 7, не в середину).

## Позиция 7 — Декомпозиция

Не потребовалась отдельная схема-вставка для веток — 8 веток укладываются в одну панорамную «шапку». Единственная точка декомпозиции — чек-лист GateProfilization на ветке 8 (см. выше), уже вынесенный по правилу «разрежь великана» на существующий внешний артефакт, а не в новую вставку внутри этой же схемы.

## Позиция 8 — Решение о генерации кода

Режим **B** — схема как рендер, не источник истины (`DRK.D.003`). Таблица `FE.M.001` уже существует и остаётся source-of-truth; эта схема — визуальное представление той же логики для DrakonHub, полезное при обучении и коммуникации с Дизайнерами-конструкторами, не для автогенерации кода. Это совпадает с явно записанным в самом различении `DRK.D.003` примером: «для большинства методов в системе, уже описанных таблицей E.18, верен режим B».

## Разбор нарративизации (NSTD.1, NSTD.2)

> Рамка: `FPF/Narrativization-and-Narrative-Studies-Principles-Framework.md`.

### NSTD.1 — Source-Structure Intake and Narrative Purpose

**Отобранные структуры источника, которые должны выжить в рендере:** 8 позиций верхнего уровня, все 10 гвардов с точной привязкой к позиции, единственная граница «без автоматической композиции» (2b↔3a), решение о режиме кода (`DRK.D.003`).

**Назначенное использование:** практика освоения метода `DRK.M.001` на живом примере (WP-31) + рабочий черновик для переноса в DrakonHub человеком.

**Что сохранено:** структура позиций и гвардов 1:1 с исходной таблицей — ни одна позиция и ни один гвард не потеряны и не объединены произвольно (проверено построчно на позиции 9 выше).

**Что упрощено (сознательно, не потеря структуры):** полный текст «Governor» (роль + ограничение) и полный текст «Контрфактика при нарушении» из таблицы `FE.M.001` не продублирован на иконах — вместо этого схема ссылается на источник по номеру позиции. Причина: ДРАКОН-икона по правилам языка короткая (панорамность требует лаконичных подписей); полный текст, продублированный на схеме, разошёлся бы с таблицей при следующей правке `FE.M.001` (тот самый риск, который `DRK.D.003` называет явно). Источник истины для точной формулировки governor/контрфактики остаётся один — таблица.

**Что было бы потеряно без этого разбора:** без явного примечания на ветке 2 читатель схемы принял бы порядок 2b→3a за физическую необходимость (визуальный порядок сверху вниз обычно читается как обязательная последовательность) — примечание явно снимает эту ложную импликацию, которую сама нотация ДРАКОН иначе создала бы неявно.

### NSTD.2 — Structure-to-Sequence Ordering

**Правило упорядочивания:** линейный порядок веток 1→2→...→8 повторяет порядок исходной таблицы, который сам уже кодирует физическую необходимость («нижний ярус нельзя проектировать после столешницы» и т.д. — обоснование есть в самой таблице `FE.M.001`, раздел «Границы без автоматической композиции»). Отдельного нового правила упорядочивания не вводилось — источник уже дал обоснованный порядок, задача рендера была его не исказить.

**Правило главного маршрута (`DRK.D.002`) применено иначе, чем в схемах с альтернативными исходами:** здесь нет конкурирующих «успешных» веток разной степени успешности — есть одна последовательность позиций и локальные циклы исправления при нарушении гварда. Поэтому «главный маршрут» — сама вертикаль силуэта (успешное прохождение без нарушений), а «правее/хуже» — не отдельная параллельная ветка, а короткий цикл возврата у каждого гварда. Это соответствует духу правила (кодировать качество исхода положением на схеме), но не его буквальной форме (параллельные вертикали) — эта адаптация зафиксирована здесь явно, а не молча.
